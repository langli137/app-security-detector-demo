# 电商评论共性问题洞察助手

## 概述

本技能用于批量分析电商商品评论，从中提取共性关键词、分类情感倾向、归纳好评亮点与差评痛点，并生成结构化洞察报告。适用于需要从大量非结构化用户评论中快速提炼可行动洞察的场景。

## 何时使用

当用户提供一批电商商品评论（文本列表、CSV评论列、或自然语言描述如「帮我分析这些评论」）并期望获得以下任一输出时触发：

- 评论情感分类（好评 / 中评 / 差评）
- 高频关键词提取与排名
- 共性好评维度与差评痛点归纳
- 用户需求挖掘与产品改进建议

不适用场景：单条评论的情感判断（过于简单，不需要此技能）；多商品竞品横向对比分析（超出范围）。

### 分析模式选择

本 Skill 支持两种分析深度，根据用户指令或输入规模自动选择：

#### 快速扫描模式（Quick Scan）

触发条件（满足任一即启用）：
- 用户明确说「快速看下」「先扫一眼」「大概有哪些问题」「只看关键词」
- 输入评论数 ≥ 300 条且用户未要求详细报告
- 用户说「只要关键词」「给我 Top N 就行」

输出内容（两项）：
1. 数据概览表（情感分布 + 置信度分布）
2. 好评 + 差评关键词 Top 10（并列展示，不做主题分析和改进建议）

快速模式不生成主题分析表、代表性原句和改进建议章节。输出末尾附一行：
「以上为快速扫描结果。如需完整洞察报告（含主题分析 + 代表性原句 + 改进建议），回复“详细分析”。」

#### 完整报告模式（Full Report）

触发条件（满足任一即启用）：
- 用户说「完整分析」「详细报告」「帮我出个报告」「全面分析」
- 输入评论数 < 300 条且未明确要求快速扫描
- 未收到任何模式指令时，**默认使用完整报告模式**

输出内容：全部报告章节（数据概览 → 待人工复核清单 → 好评洞察 → 差评洞察 → 改进建议 → 免责声明）

分析模式在「第一步」预处理完成后确定，后续步骤按选定模式执行。

## 标准工作流程

接收到用户输入的评论文本后，按以下步骤依次执行，不得跳过任何步骤。

### 第一步：数据接收与预处理

1. 接受用户提供的评论文本。支持格式：每行一条评论的纯文本、JSON 字符串数组、Markdown 列表。
2. 统计评论总数。
3. 过滤无效评论：去除纯表情符号、纯标点符号、长度不足 2 个字符、完全重复的评论行。
4. 输出有效评论数，说明过滤掉的数量及过滤原因。

### 第一步附：极端输入边界处理

预处理完成后立即检测以下场景并触发对应策略。边界检查先于「分析模式选择」和「第二步」情感分类执行。

| 场景 | 触发条件 | 处理策略 |
|------|---------|---------|
| 零有效评论 | 有效评论 = 0 | 终止分析，输出：「经预处理后无有效评论（过滤原因：全部为纯符号 / 重复 / 过短）。请检查数据源。」 |
| 评论数过少 | 有效评论 < 5 条 | 跳过主题归纳（第四步）和改进建议（报告第四部分），仅输出情感分类 + 关键词列表。报告中标注：「样本量不足（<5 条），主题分析和改进建议不可靠，已跳过。」 |
| 全部好评 | 差评数 = 0 | 差评洞察部分输出「本次分析中无差评评论」，跳过差评主题表和差评关键词。 |
| 全部差评 | 好评数 = 0 | 好评洞察部分输出「本次分析中无好评评论」，跳过好评主题表和好评关键词。 |
| 全中评 | 好评数 = 0 且 差评数 = 0 | 输出情感分类结果后终止，标注：「所有评论均为中性，无法提取显著的好评 / 差评特征。当前评论可能为纯事实陈述或质量无关内容。」 |
| 超大批量 | 有效评论 > 500 条 | 强制启用「快速扫描模式」（无论用户是否指定），并附加提示：「已分析 N 条评论（总量 >500），当前为快速扫描模式。如需特定维度的深度分析，可筛选评论子集后重新提交。」 |
| 含外语混杂 | 中文评论占比 < 70% | 输出中附带提示：「评论中含较多非中文内容（占比约 X%），部分关键词和主题可能遗漏非中文信息。对于非中文为主的评论集合，建议单独提交分析。」 |

### 第二步：情感分类与置信度评估

对每条有效评论做两项独立判断，输出二元结果。分类依据评论中出现的具体情感词和整体语境，而非仅凭单一关键词匹配。

#### 2.1 情感倾向分类（三选一）

- **好评**：表达满意、赞扬、推荐、超出预期等正面情绪
- **中评**：纯事实陈述无明显情感、优缺点各半、情感中性
- **差评**：表达不满、抱怨、失望、退货意向等负面情绪

#### 2.2 置信度评估（三选一，独立于情感倾向）

- **高置信度（≥80%）**：评论含明确情感词、单一倾向、无转折语气。例：「音质非常好，推荐购买」→ 好评 / 高
- **中置信度（60-80%）**：含情感词但有转折，或情感强度弱、表述简短。例：「音质还行，但续航一般」→ 中评 / 中；「还行吧」→ 中评 / 中
- **低置信度（<60%）**：纯场景描述无情感词、纯吐槽无指向、反语、讽刺、单一感叹词、纯 emoji 表达。例：「用了三天」→ 中评 / 低；「呵呵」→ 中评 / 低

#### 2.3 统计汇总

- 分别统计好评 / 中评 / 差评在高 / 中 / 低三个置信度层级中的分布
- 统计并输出好评率、中评率、差评率（近似百分比，保留一位小数）
- **后续分析（第三步关键词提取、第四步主题归纳）仅基于高置信度 + 中置信度的评论**。低置信度评论不参与关键词提取和主题统计，统一归入「待人工复核清单」

#### 2.4 待人工复核清单（写入报告）

如存在低置信度评论，在报告中「数据概览」之后插入独立小节：

| 序号 | 评论原文 | 机判倾向 | 置信度 | 建议复核方向 |
|------|---------|---------|--------|-------------|
| 1 | "用了三天" | 中评 | 低 | 判断是否为省略表达的差评 |
| 2 | "呵呵" | 中评 | 低 | 判断是否为讽刺性差评 |
| ... | ... | ... | ... | ... |

如无低置信度评论，该小节输出一行：「本次分析无低置信度评论，所有结果均为中高置信度。」

### 第二步附：评论者可信度权重

在进入关键词提取之前，对每条参与统计的有效评论（高置信度 + 中置信度）计算一个可信度权重系数（范围 1.0-2.0），用于后续所有计数和占比的加权计算。加权不影响情感分类和置信度评估的结果。

#### 权重计算规则

1. **基础权重**：每条评论初始值 = 1.0

2. **长度加权**（基于字数，不含标点和 emoji）：
   - ≥50 字 → +0.5
   - 20-49 字 → +0.3
   - 10-19 字 → +0.1
   - <10 字 → +0

3. **具体性加权**（判断评论是否包含场景或数值描述）：
   - 含具体使用场景描述（如「跑步时」「地铁上」「开会用」「健身房」）→ +0.3
   - 含数值或量化描述（如「用了 3 个月」「续航 4 小时」「第 2 次购买」「降价了 20 块」）→ +0.2
   - 同时含场景和数值 → +0.5

4. **最终权重** = min（基础权重 + 长度加权 + 具体性加权，2.0）

#### 加权应用

适用于以下所有统计环节：
- 关键词频次 = Σ（每条含该关键词的评论的权重），而非简单计数
- 主题提及次数 = Σ（该主题下所有相关评论的权重之和）
- 各项占比 = 加权提及次数 / 总加权评论数

不适用加权的情况：情感倾向分布（好评 / 中评 / 差评计数）、置信度分布（高 / 中 / 低计数）——这些使用原始条数。

#### 应用示例

| 评论 | 字数 | 场景 | 数值 | 权重 | 说明 |
|------|------|------|------|------|------|
| 「还行」 | 2 | 无 | 无 | 1.0 | 最短评论，无额外权重 |
| 「音质不错，续航还行」 | 9 | 无 | 无 | 1.0 | 不到 10 字 |
| 「戴着跑步不会掉，防水也好」 | 12 | 跑步 | 无 | 1.1 + 0.3 = 1.4 | 有场景 |
| 「用了三个月音质稳定，降噪通勤够用，跑步偶尔掉，对得起价格」 | 28 | 通勤、跑步 | 三个月 | 1.3 + 0.5 = 1.8 | 长度+场景+数值 |

在报告「数据概览」末尾附一行：「本次分析的统计均基于加权计数（权重范围 1.0-2.0，数值越大表示评论信息量越高）。情感和置信度分布使用原始条数。」

### 第三步：关键词提取

分好评和差评两个集合分别提取高频关键词。**统计使用加权计数**（每条评论的频次贡献 = 该评论的可信度权重，见「第二步附」）：

1. 对每条评论识别 2-5 字的有意义短语
2. 统计每个关键词 / 短语在对应集合中的加权出现频率（频次 = Σ权重，而非简单条数）
3. 去除通用停用词（「的」「了」「是」「我」「很」「也」「就」等无意义高频词）
4. 按加权频次降序排列，分别输出好评 Top 15 和差评 Top 15 关键词

**核心约束**：所有关键词必须是原始评论中实际出现的词语或短语，不得推断或编造用户未提及的内容。

### 第三步附：关键词形态归一化

在原始频次统计完成后、输出 Top N 排名之前，对已提取的关键词进行同义归并。目的是将同一用户关注点的不同口语化表达合并为一个统一计数，避免信号被表达多样性稀释。

#### 归并规则

以下规则按顺序应用，每条规则处理上一条规则的输出：

**规则 1：剥离程度副词**

从头尾识别并移除以下修饰词，保留核心评价词：
- 前导程度副词：「很」「非常」「特别」「挺」「太」「比较」「有点」「稍微」「超级」
- 示例：「很好」→ 剥离「很」→ 归入「好」；「非常差」→ 剥离「非常」→ 归入「差」；「挺快的」→ 剥离「挺」和「的」→ 归入「快」

**规则 2：近义褒贬词归一**

褒义组（指向同一含义「好」）：「不错」「还行」「可以」「OK」「挺好」「给力」「赞」→ 统一归为「好」
贬义组（指向同一含义「差」）：「不好」「不行」「差」「垃圾」「烂」「糟糕」→ 统一归为「差」

**规则 3：同义短语合并**

将语义相同的短语变体合并为一个代表短语：
- 「续航好」「续航不错」「续航可以」「续航给力」「耐用」→ 统一归为「续航好」
- 「断连」「断线」「断开」「连不上」「掉线」→ 统一归为「断连」
- 「戴着不舒服」「耳朵疼」「夹耳朵」→ 统一归为「佩戴不适」
- 「音质好」「声音好」「音效好」→ 统一归为「音质好」

合并时选择一个最具代表性、最高频的短语作为主键，其余变体的频次累加到主键。

#### 归并输出

- 归并后的关键词按合并频次重新排序，输出好评 Top 15 和差评 Top 15
- 关键词名称使用合并后的代表短语
- 在关键词列表末尾附一行小字：「以上关键词已做同义归并处理，括号内为合并后频次」
- 原始未归并的关键词也保留一份（不写入报告），供自查回溯时核对

### 第四步：共性主题归纳

将语义相近的关键词归并为主题簇：

1. 对好评关键词进行语义聚类，提炼 3-8 个好评主题（如「音质体验」「续航表现」「佩戴舒适度」「性价比」「物流服务」等）
2. 对差评关键词进行语义聚类，提炼 3-8 个差评主题（如「连接稳定性」「续航不足」「材质做工」「客服响应」「包装损坏」等）
3. 统计每个主题在总评论中的出现频率和占比
4. 为每个主题选取 3-5 条最具代表性的原始评论作为例证（必须引用原文，不得改写）

### 第四步附一：改进建议优先级评分（仅完整报告模式）

在主题归纳完成后，对每条差评主题进行二维优先级评分，确保「用户需求挖掘与建议」章节的输出按紧急程度排序而非平铺列出。

#### 评分规则

针对每个差评主题，计算两个独立分数后相乘：

**影响面分数（1-5）**：基于该主题的加权提及次数占全部差评中高置信度加权总数的比例。
- <5% → 1 分
- 5-10% → 2 分
- 10-20% → 3 分
- 20-30% → 4 分
- >30% → 5 分

**严重度分数（1-5）**：基于该主题代表性差评原文中的情绪强度和后果描述。必须依据原始评论中的实际表述定级，不得凭空判断。
- 1 分（轻微）：不影响使用的体验瑕疵。如「盒子有点旧」「颜色和图片略有差异」
- 2 分（轻度）：轻度影响体验或外观感受。如「白色不耐脏」「耳机仓容易沾指纹」
- 3 分（中等）：明显影响正常使用但可容忍。如「续航只有宣传的一半」「触摸太灵敏容易误触」
- 4 分（较严重）：严重影响正常使用。如「频繁断连没法用」「充电仓盖子一周就松了」
- 5 分（严重）：安全风险或功能彻底失效。如「充电发热严重不敢用了」「用了三天就彻底坏了」

如评论仅说「XX 不行」但未描述具体程度 → 默认严重度 3 分（中等），并在表格中标注「基于有限信息估计」。

**综合优先级** = 影响面分数 × 严重度分数（范围 1-25）

#### 优先级分级

- ≥20 分：🔴 紧急（建议本周内修复）
- 12-19 分：🟡 重要（建议本月内修复）
- ≤11 分：🟢 一般（列入下个迭代计划）

#### 输出格式

在「用户需求挖掘与建议」章节按优先级降序输出（不使用原平铺列表格式）：

| 优先级 | 差评主题 | 影响面 | 严重度 | 综合评分 | 改进建议 |
|--------|---------|--------|--------|---------|---------|
| 🔴 紧急 | 连接稳定性 | 23% 加权差评 (4分) | 频繁断连无法正常使用 (4分) | 16 | 升级蓝牙固件... |
| 🟡 重要 | 续航不足 | 16% 加权差评 (3分) | 续航仅宣称一半 (3分) | 9 | 优化电量管理... |
| 🟢 一般 | 包装简陋 | 8% 加权差评 (2分) | 包装体验不佳 (2分) | 4 | 改用彩盒... |

如只有 ≤2 个差评主题，无需输出优先级列和红绿灯标记，仅保留改进建议表格。

### 第四步附二：主题共现分析（仅完整报告模式）

主题归纳完成后，额外构建好评和差评的主题共现矩阵，发现跨主题的用户关注模式。共现分析仅对加权提及 ≥5 条的交叉关系做统计，低于此阈值的不展示。

#### 构建方法

对每条中高置信度评论，提取其命中的所有主题标签（好评评论提取好评主题标签，差评评论提取差评主题标签）。统计任意两个主题标签在同一条评论中同时出现的加权评论数。

#### 输出格式

好评主题共现矩阵：

| 好评共现 | 音质 | 续航 | 性价比 | 佩戴 | 降噪 |
|---------|------|------|--------|------|------|
| 音质    | -    | 15   | 28     | 8    | 22   |
| 续航    | 15   | -    | 12     | 6    | 5    |
| 性价比  | 28   | 12   | -      | 9    | 18   |
| 佩戴    | 8    | 6    | 9      | -    | 4    |
| 降噪    | 22   | 5    | 18     | 4    | -    |

差评主题共现矩阵（同理构建）。

#### 矩阵下方解读

基于共现数据输出 1-3 条关键发现：

- 高频共现对（加权 ≥20）：「音质 + 性价比」共现 28 次，说明音质是用户感知高性价比的核心驱动力
- 中频共现对（加权 10-19）：「音质 + 降噪」共现 22 次，主动降噪是音质好评的重要关联因素

### 第五步前置：动态内容写入表格前的安全处理

以下规则适用于**所有**写入 Markdown 表格的动态字段——代表性原句、关键词（含短语）、主题名称——必须在写入表格单元格之前逐条处理。处理后语义不变但破坏性字符已消除。处理按以下顺序执行：

#### 表格分隔符与结构破坏符

| 原始字符 | 替换为 | 原因 |
|----------|--------|------|
| `\|`（竖线，U+007C） | `／`（全角斜线，U+FF0F） | 破坏 Markdown 表格列分隔，必处理 |
| `\n`、`\r`（换行、回车） | 一个半角空格 ` ` | 破坏表格行结构，必处理 |

#### HTML / XSS 注入风险字符

| 原始字符 | 替换为 | 原因 |
|----------|--------|------|
| `<`（U+003C） | `＜`（全角小于号，U+FF1C） | 防止 HTML 标签注入 |
| `>`（U+003E） | `＞`（全角大于号，U+FF1E） | 防止 HTML 标签注入 |
| `&`（U+0026） | `＆`（全角与号，U+FF06） | 防止 HTML 实体注入 |

#### Markdown 语法注入

| 原始模式 | 处理方式 | 原因 |
|----------|----------|------|
| 反引号 `` ` `` | 删除（从原文中移除该字符） | 防止代码块 / 内联代码注入 |
| `[text](url)` 形式的链接 | 剥离为纯文本 `text`，丢弃 URL | 防止可点击链接注入 |
| `![alt](url)` 形式的图片 | 替换为 `[图片]`，丢弃 URL | 防止外部资源加载 |
| `javascript:` 协议（大小写不敏感） | 整段替换为 `[已移除]` | XSS 攻击向量，一票否决 |
| `data:` 协议（大小写不敏感） | 整段替换为 `[已移除]` | XSS 攻击向量，一票否决 |

#### CSV 公式注入（含潜在导出场景）

以下操作针对每个表格单元格单独执行：

1. **去除前导空白**：从内容开头依次剥离以下字符直至遇到首个非空白字符——半角空格 `U+0020`、制表符 `U+0009`、全角空格 `U+3000`
2. **判断首个非空白字符**：若去除前导空白后首个字符为 `=` `+` `-` `@` 中任意一个，则在整个**原始内容最开头**（去除前导空白前的位置）插入一个半角单引号 `'`（U+0027）作为纯文本前缀；否则不做处理

**单引号前缀原理**：Excel / CSV 解析器将单元格开头的单引号识别为「强制文本模式」，单引号本身不在单元格中显示，且后续内容不会被当作公式执行。

示例：

| 原始内容 | 去除前导空白后首字符 | 处理结果 | 表格中显示 |
|----------|---------------------|----------|-----------|
| `=SUM(A1:A10)` | `=` | `'=SUM(A1:A10)` | =SUM(A1:A10)（不执行） |
| ` =SUM(1,1)`（前导空格 + 公式） | `=` | `' =SUM(1,1)` | ` =SUM(1,1)`（不执行） |
| `\t@cmd`（制表符 + `@`） | `@` | `'\t@cmd` | `\t@cmd`（不执行） |
| `　+8613800138000`（全角空格 + `+`） | `+` | `'　+8613800138000` | `　+8613800138000`（不执行） |
| `- 降价了` | `-` | `'- 降价了` | - 降价了（不执行） |
| `正常评论内容` | `正`（不在 `=+-@` 中） | 不做处理 | 正常评论内容 |

#### 处理执行顺序

必须严格按以下顺序执行，不可颠倒：

1. 先处理 `javascript:` 和 `data:` 协议（全文搜索替换为 `[已移除]`）
2. 再处理 Markdown 链接和图片（剥离为纯文本）
3. 再处理表格分隔符 `|`、换行符
4. 再处理 HTML 字符 `<` `>` `&`
5. 再删除反引号
6. 最后执行 CSV 公式注入防护：去除前导空白（空格、制表符、全角空格），若首个非空白字符为 `= + - @` 则在原始内容最开头插入单引号 `'`

如某条评论经上述处理后变成空字符串或仅剩标点符号，则在表格中填入 `[内容已过滤]`。

#### 处理范围

以下动态字段**必须**全部经过上述安全处理才能写入表格：
- 代表性原句（好评 / 差评主题表中的「代表性原句」列）
- 所有关键词和短语
- 所有主题名称（如「音质体验」「续航表现」等）
